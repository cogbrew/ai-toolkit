# 주석과 독스트링 세부

## 적는 것과 적지 않는 것

| 적음 | 적지 않음 |
|---|---|
| 지우면 깨지는 것. 예: 보관이 삭제보다 먼저임 | 지난 사연. 예: 한때 세 곳에 있었음 |
| 숫자의 근거. 예: MAX_ATTEMPTS 옆의 간혹 연결 오류가 난다는 설명 | 읽는 사람에게 이미 자명한 것 |
| 순서가 뜻을 바꾸는 곳 | 문서에 있는 정책, 계약 전문 |

- 코드가 명확하면 주석은 두지 않음. 남기는 것은 코드만 봐서는 모르고 지우면 깨지는 이유 한 줄뿐.
- 정책은 문서가, 이유는 커밋이, 코드는 여기서 틀릴 수 있는 것만 가짐.

## 독스트링은 셋으로 갈림

| 상태 | 처리 | 예 |
|---|---|---|
| 코드를 그대로 재진술 | 지움 | 읽기 전용. 아래 http_method_names 가 이미 말함 |
| 이유만 남김 | 한 줄로 | 기록은 남기는 것이지 고치는 것이 아님 |
| 코드에 없는 사실 | 남김 | 여기서 만드는 것은 배포가 아니라 연결임 |

- 가르는 물음은 하나. 이 문장을 지우면 누가 무엇을 잘못하는지. 답이 없으면 지움.
- 읽기 전용이라는 말은 코드가 말하지만 왜 읽기 전용인지는 말하지 않음. 그 이유 한 줄이 나중에 수정 API 를 열려는 사람을 멈춰 세움.
- 정책이 적힌 독스트링은 문서에 있는지 확인한 뒤 지움. 독스트링이 그 정책의 유일한 기록일 수 있음.

## 함수와 테스트의 독스트링
- 무엇을 하는지 한 줄, 돌려주는 모양 설명, 테스트 이름을 되풀이하는 문장은 쓰지 않음. 형식으로 붙인 독스트링은 코드가 바뀌면 혼자 낡음.
- 남기는 것은 지켜야 할 순서(삭제는 지우기 전에 부른다), 테스트가 쓰는 비자명한 기법 같은 한 줄뿐. 그마저 한 줄 주석으로 충분하면 주석으로 둠.
- 왜 존재하는지는 커밋 메시지가 가짐.

## 프레임워크가 하는 일은 설명하지 않음
- 훅이나 생명주기 메서드에 이 훅은 저장 직전에 불린다는 설명을 붙이지 않음. 그 프레임워크로 일하는 사람은 아는 내용임.
- 적을 것은 이 프로젝트가 그 훅에서 무엇을 하기로 했는지 중 코드로 안 보이는 것뿐.

## 규칙은 강제로 지킴
- 여기서는 X 를 임포트하지 않는다 같은 문장은 아무것도 막지 못함. 어길 사람은 문장을 읽고도 어김.
- 중요하면 린트나 테스트로 막고, 그 정도가 아니면 적지 않음.

## 보이는 대로 고치지 않음
- 남이 쓴 코드에서 주석 문제가 보이면 고치지 않고 말함. 내가 이번에 쓴 코드는 쓰는 자리에서 지킴.
- 정리는 사람이 정한 때 전체를 한 번에 훑음. 그때그때 고치면 기준이 바뀔 때마다 다시 손대게 됨.
