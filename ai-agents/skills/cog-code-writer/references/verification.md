# 문서 확인과 검증 세부

## 한 가지는 한 곳에
- 원본에서 자동으로 나오는 값은 스스로 규칙을 갖지 않음.
  - A 가 유니크하고 B 도 유니크함: 기술 구조이므로 제약이 둘임.
  - B 는 A 에서 나옴: 정책이므로 규칙은 하나임.
- 둘로 읽으면 둘을 잇는 코드가 생김. 한쪽 오류를 다른 쪽으로 옮기고, 어느 쪽을 보여줄지 판단하는 코드임. 하나로 보면 그 코드가 통째로 없음.
- 기술 구조보다 정책을 먼저 읽음.
- 프레임워크가 모델에서 자동으로 만들어 주는 것(유니크, 필수, 타입 변환)을 손으로 다시 짜고 있다면 앞에서 무언가 빼 놓았다는 신호. 메우기 전에 왜 비었는지 확인.
- 한 개념은 한 이름. 새 이름을 짓기 전에 같은 개념을 이미 정한 말이 있는지 모델 칸, 파라미터, 라벨 상수에서 찾음. 한 층에서 정한 이름을 다른 층에서 다시 지으면 같은 개념이 두 이름으로 갈림.

## 옮기고 이름을 바꾼 뒤 문서 확인

코드를 옮기면 문서가 옛 자리를 가리킨 채 남음. 아래를 전부 확인. 하나만 건너뛰어도 조용히 낡음.

| 확인 | 방법 |
|---|---|
| 링크가 실재하나 | 모든 링크 경로를 모아 파일이 있는지 확인 |
| 본문의 경로가 실재하나 | 백틱 안의 경로도 같은 검사. 링크만 보면 절반을 놓침 |
| 목차가 실제 파일과 맞나 | 목차가 나열한 것과 디렉토리에 있는 것을 양방향으로 대조 |
| 절 번호 참조가 살아 있나 | 절을 하나 지우면 뒤가 전부 밀림 |
| 옛 경로가 남았나 | 옮기기 전 이름으로 전체를 한 번 검색 |

- 숫자와 목록은 코드가 원본. 열린 API, 마이그레이션 번호, 테스트 수, 파일 개수는 문서끼리 맞추지 않고 코드에서 다시 뽑음.
- 도구는 정하지 않음. 환경에 있는 것으로 함. 적어 두면 그것이 또 낡음.
- 언제 대조했는지 적음. 안 적으면 다음 사람이 처음부터 다시 봄.

무엇을 고치면 어디를 함께 보나

| 고친 것 | 함께 볼 곳 |
|---|---|
| API 를 더하거나 지움 | 그 스택 문서의 API 목록 |
| 모델 필드, 마이그레이션 | 그 스택의 현재 상태, 도메인 문서의 필드 매핑 |
| 정책을 정함 | 저장소의 설계 문서 |
| 지우면 안 되는 코드를 만듦 | 그 도메인의 왜 이렇게 되어 있나 |
| 문서를 옮김 | 위 다섯 가지 검사 전부 |

## 지키려는 것은 깨뜨려서 확인

테스트를 썼으면 지키려는 코드를 일부러 되돌려 그 테스트가 실제로 실패하는지 확인.

- 캐스케이드를 바꿔 봄: 이력이 사라지는가
- 묶어 읽기를 풀어 봄: 쿼리가 늘어나는가
- 가리기를 빼 봄: 비밀이 로그에 나오는가

통과하는 테스트는 아무것도 증명하지 않음. 깨지는 것을 봐야 그 테스트가 무엇을 지키는지 알 수 있음.

## 값으로 확인
- 맞아 보인다로 끝내지 않음. 화면은 좌표와 계산된 스타일로, 성능은 쿼리 수로, 동작은 실제 저장된 값으로 확인.
- 회귀부터 확인. 새로 만든 것보다 이전 것이 그대로 도는지가 먼저.
