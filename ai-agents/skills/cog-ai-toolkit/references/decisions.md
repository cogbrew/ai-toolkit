# 결정 기록과 아직 정하지 않은 것

## 결정 기록 (2026-11-11)

- 폴더 이름 `ai-agents/`: 도구별 폴더를 한 곳에 묶기 위해 정했다. `agents/` 는 서브에이전트 폴더와 혼동되고, `global/`·`home/`·`shared/`·`rules/` 는 의미가 맞지 않거나 도구가 쓰는 이름과 겹쳐 제외했다.
- 스킬은 `ai-agents/skills/` 한 곳에 둔다: 최상위 `skills/` 를 없애고 `ai-agents/` 가 지침과 스킬을 함께 담는다. 세 도구가 같은 `SKILL.md` 형식을 읽으므로 진입 파일을 도구마다 두지 않고 한 벌만 둔다. 한 도구에만 쓰는 스킬은 `ai-agents/<도구>/skills/` 에 둔다.
- 래퍼 폴더 방식: `slop-rewrite` 스크립트가 자기 위치에서 루트를 계산해 내부 구조를 바꿀 수 없다. 그래서 가져온 프로젝트를 `project/` 에 통째로 담고 진입 파일을 곁에 둔다. 상대경로만 쓰므로 저장소를 옮겨도 동작한다. Claude 에서 인식, 상대경로 따라가기, 스크립트 실행, 목록에 중복 없음을 시험했다.
- 연결 스크립트(`scripts/install_ai_toolkit.sh`): 기본은 계획만 출력하고 `--apply` 로 실행한다. 스킬 하나마다 링크하며 도구 폴더 전체는 링크하지 않는다. 이미 있는 항목은 덮어쓰지 않고 `--backup` 일 때만 옮겨 둔다. 삭제 명령은 쓰지 않는다. 별칭 `~/.ai-toolkit`(저장소 위치)도 만든다. 도구별 경로와 예약 이름은 `scripts/targets.conf` 에 둔다.
- 이름 규칙: 직접 만든 스킬만 `cog-` 접두사를 붙이고, 가져온 스킬(`slop-rewrite`, `taste-builder`, `styleguide-builder`)은 이름을 유지한다. 직접 만든 스킬(`cog-code-writer`, `cog-django`, `cog-vue`, `cog-report-writer`)은 작성 기준과 시험을 거쳐 만들었다.
- 공통 지침은 `ai-agents/AGENTS.md` 한 파일: 도구 전용 줄이 없어 한 파일로 시작했다.
- 다루는 도구: Claude Code, Codex, Antigravity(앱·CLI). Antigravity IDE 는 쓰지 않는다. Gemini CLI 는 Antigravity CLI 로 대체되어 다루지 않는다.
- 유지보수를 스킬(`cog-ai-toolkit`)로 둔 이유: 어느 도구에서든 어느 프로젝트에서든 갱신이 필요할 수 있어서 직접 호출할 수 있는 스킬이 맞다. 참조문서 방식은 자동 호출의 확실성이 문제였던 스킬 방식(4개 중 2개 호출)보다 읽히는 비율이 높았지만(4/4), 직접 호출에는 그 약점이 없고 세 도구에 링크로 깔려 다른 프로젝트에서도 쓸 수 있다.
- 루트 `AGENTS.md` 의 안내 문구는 세 차례 고쳤다. 처음 문구는 「새 스킬 추가」 요청에서 읽지 않았고, 두 번째 문구는 「스킬 만들어줘」 같은 작업 요청에서 읽지 않았다. 작업 시점(「…하는 요청을 받으면, 파일을 쓰기 전에」)을 명시한 문구에서 작업 요청 3/3 은 읽었고 무관한 요청 3/3 은 읽지 않았다. 지금의 루트 안내는 이 결과를 따른다.
- `cog-code-writer` 의 범위: 코드를 쓸 때 지킬 기본 규칙(주석과 독스트링, 예시 데이터, 함수와 파일 구성, 한 곳에만 두기, 문서 확인, 검증)만 담는다. 코드 검수 방식과 설계안 제시 규칙은 쓰기 규칙과 성격이 달라 넣지 않았다. 문서는 명사형 종결로 쓰고 특수기호를 쓰지 않으며 윤문 검사기의 원칙 층을 통과시켰다. 이름은 짧게 `cog-code-writer` 로 정했다.
- `cog-code-writer` 를 코드 작성 때마다 읽히게 하는 방식: Claude 시험에서 스킬만 두면 코드 작성 요청 10개 중 8개, 스킬과 전역 지침 한 줄을 두면 10개 모두 호출됐다. 그래서 스킬과 지침 한 줄(`ai-agents/AGENTS.md` 의 코드 절)을 둔다. 규칙 본문을 지침에 직접 넣는 방식은 같은 규칙이 두 곳에 생겨 어긋나기 쉬워 택하지 않았다. 호출된 경우 규칙이 지켜졌고(독스트링 0개, 가상 이름, 문서 확인 5항목), 아무것도 없는 기준에서는 어긋났다. 과제당 1회 시험이다.
- `cog-django` 의 범위: Django 백엔드의 기본 구성 규칙(디렉토리 구조와 층, apps·modules·utils·extensions 구성, settings 분리, .env 와 필수 변수 검사와 기능 스위치, accounts 와 core 구성, 등록 위치, 범용 함정, 마이그레이션)만 담는다. 범용 규칙만 담았고, `.env` 구조와 settings 구성은 프로젝트 `infra-iscim-app` 의 코드(변수 이름만 추출하고 값은 읽지 않음)와 그 프로젝트의 `CLAUDE.md` 에서 뽑았다. 그 프로젝트의 `backend` 스킬은 근거로 쓰지 않았다.
- `cog-django` 에서 뺀 것: 인증과 권한 체계, 배치와 외부 연동(실행 리포트, 락, 재시도, 자격증명), DRF API 설계, 로깅 설계(로그 테이블, 로그 봉투), 프로젝트 고유 예시. 후속 스킬 후보로 둔다.
- `cog-django` 에 에이전트가 일반 Django 지식으로 추가한 것: N+1, update 와 bulk_update 의 시그널·auto_now 미호출, transaction.on_commit, 적용된 마이그레이션 수정 금지, 마이그레이션 누락 확인, ruff 기본값, 새 환경변수를 더할 때 읽는 코드와 필수 목록과 .env.example 을 함께 고친다는 규칙. 마지막 규칙은 코드 구조에서 추정한 것이다.
- `cog-django` 호출 방식: 직접 호출과 description 자동 호출만 쓰고 전역 지침 한 줄은 두지 않는다. Claude 시험(과제당 1회)에서 Django 요청 12개 중 11개가 호출됐고, 미호출 1개는 디버깅 질문이라 description 에 디버깅 구절을 더했다. 보강 뒤 같은 유형 3개가 모두 호출됐다. Django 가 아닌 요청 8개(다른 언어 코드, 비코드, 다른 언어 디버깅)에서는 호출되지 않았다. 동작 시험에서 스킬 항목 언급은 27/27, 스킬이 없을 때는 10/27 이었다. 이 점수는 스킬의 어휘로 잡은 항목이라 스킬이 쓰이는지만 보여 주고 규칙의 타당성은 보여 주지 않는다.
- `cog-vue` 의 범위: 프론트엔드 기본 규칙(파일 위치와 앱 경계, 이름 짓기, 컴포넌트와 Pinia 스토어 작성, 스타일 토큰과 Nuxt UI 를 Vite 에서 쓸 때의 차이, Vite 설정과 환경변수와 린트)만 담는다. 범용 규칙만 담았고, 설정 파일 구성은 프로젝트 `infra-iscim-app/frontend` 의 vite.config, tsconfig, oxlint, oxfmt, editorconfig, gitignore 와 코드에서 뽑았다(환경변수 파일은 읽지 않고 VITE_ 변수 이름만 코드에서 추출).
- `cog-vue` 에서 뺀 것: 데이터 테이블, 읽기 전용 상세, 페이지 헤더, 토스트와 모달 흐름, 폼 검증 같은 화면 패턴(data-tables, detail-view, page-header, ux-patterns 로 나눌 후보). 프로젝트 부품(AppDataTable, useListQuery 등)에 묶인 내용이 많아 후속 스킬 후보로 둔다. 프로젝트 고유 화면 예시는 넣지 않았다.
- `cog-vue` 에 에이전트가 추가한 것(프로젝트에서 확인하지 못한 일반 지식): import.meta.env 타입 선언(env.d.ts)을 함께 고친다는 규칙, 환경변수 읽는 위치를 한곳으로 모은다는 규칙, VITE_ 변수에 비밀 값을 넣지 않는다는 규칙, autoImport 로 생성되는 dts 를 직접 고치지 않는다는 규칙, 개발 중 console 을 커밋하지 않는다는 규칙, 린트로 앱 경계와 상대경로 금지가 강제되는지 확인한다는 규칙, 패키지 설치 시 lock 파일 확인.
- `cog-vue` 호출 방식: 직접 호출과 description 자동 호출만 쓰고 전역 지침 한 줄은 두지 않는다. Claude 시험(질문당 1회)에서 Vue 요청 4개(파일 위치, 색 클래스, 액션 이름, 빈 화면 원인)는 모두 호출됐고, Vue 와 무관한 요청 3개(파이썬 코드, Django 질문, README 문단)는 호출되지 않았다. 동작 시험은 하지 않았다.
- `cog-report-writer` 의 범위: 보고서의 목적, 섹션 흐름(요약, 배경, 현재 상황, 본론, 결론, 부록), 리스크와 이슈 기준(기술, 비용, 운영), 일관성과 보안, 디자인(색 체계, 형식별 적용, HTML 기본 CSS)만 담는다. 문체 규칙(개조식 종결, 어휘, 항목 길이)은 `slop-rewrite` 의 개조식 보고서 작성 가이드라인(792줄)과 대부분 겹쳐 담지 않고 그쪽에 맡긴다. 같은 규칙이 두 곳에 생겨 어긋나는 것을 막기 위해서다. CSS 는 파일(`references/report-base.css`)로 분리했다.
- `cog-report-writer` 에 에이전트가 추가한 것: 자료에 없는 사실을 지어내지 않는다는 규칙, 결론을 낼 수 없으면 판단 유보 사유를 첫 부분에 쓴다는 규칙, 서식과 이 스킬과 가이드라인이 어긋날 때의 우선순위, 색만으로 뜻을 전하지 않는다는 규칙, 근거 없는 가정을 리스크 근거로 쓰지 않는다는 규칙, 모바일 확인.
- `cog-report-writer` 호출 방식: 직접 호출과 description 자동 호출만 쓴다. Claude 시험(질문당 1회)에서 보고서 구성, 방안 검토, 리스크 정리, HTML 디자인 요청 4개는 모두 호출됐다. 보고서 문장 윤문 요청은 호출되지 않고 `slop-rewrite` 가 호출됐다. 파이썬 코드, README, 이메일 요청 3개는 호출되지 않았다. 동작 시험은 하지 않았다.

- `cog-vue-uikit` 의 범위: 공용 UI 부품(App* 부품과 use* 컴포저블)으로 만드는 화면 패턴(목록, 읽기 전용 상세, 페이지 헤더, 토스트와 모달과 폼)만 담는다. 프레임워크와 무관한 원칙은 `references/common.md` 에, @nuxt/ui 구현 규칙은 `references/frameworks/nuxt-ui/` 의 패턴별 파일 4개에 둔다. 프레임워크마다 패턴별 구현이 다르므로 폴더를 프레임워크별로 나누고 `common.md` 로 공통 원칙의 중복을 막았다. `cog-vue` 에 넣지 않은 이유는 이 규칙이 사용자의 커스텀 부품에 묶여 있어 부품이 없는 프로젝트에서 읽히면 안 되기 때문이다.
- `cog-vue-uikit` 의 근거: 프로젝트 `infra-iscim-app` 의 `frontend` 스킬 사본과 `ai-config` 본 4개 문서(data-tables, detail-view, page-header, ux-patterns)를 읽어 범용 원칙과 @nuxt/ui 구현으로 나눴다. 두 본은 3~4줄씩 다르고 `ai-config` 본이 프로젝트 고유 표현을 일반화해 두었다. 뺀 것은 프로젝트 고유 화면과 용어(IDP 리포트, 배포 관리 등), 기능 권한 컴포저블(`useFeaturePerms`) 사용법, 프로젝트 문서 참조다. 나누는 경계는 에이전트가 판단했고 확인이 필요하다.
- `cog-vue-uikit` 호출 방식: 직접 호출과 description 자동 호출만 쓴다. Claude 시험(질문당 1회)에서 App* 부품을 쓰는 화면 요청 4개(목록 컬럼과 정렬, 확인 모달 실패 표시, 모달 재오픈 에러, 상세 배치)는 모두 호출됐고, 폴더 구조 질문과 파이썬 코드와 보고서 목차 3개는 호출되지 않았다. 동작 시험은 하지 않았다.
- 범용 스킬(`cog-django`, `cog-vue`, `cog-vue-uikit`)과 프로젝트 스킬의 구분: 범용 규칙은 `ai-toolkit` 에 두고, 프로젝트 스킬과 지침에는 그 프로젝트의 사실(구조 현황, 명령, 화면과 메뉴 목록, 도메인 용어, 백엔드 계약)만 둔다. 같은 규칙이 두 곳에 있으면 어긋난다.
- `cog-llm-wiki`: Astro-Han/karpathy-llm-wiki(MIT, Karpathy 의 LLM Wiki 방식을 구현한 커뮤니티 스킬)를 개인용으로 가져와 `SKILL.md` 의 `name` 만 바꿨고 나머지는 원본과 같았다(diff 로 확인, 2026-11-13 이후 폴더 이름도 바꿨다. 아래 「폴더 이름」 항목). 직접 고쳐 쓸 것이라 가져온 스킬의 래퍼 폴더 방식을 쓰지 않고 `cog-` 접두사 스킬로 `ai-agents/skills/cog-llm-wiki/` 에 두었다. 가져온 것은 `SKILL.md`, `references/`(템플릿 4개), `scripts/check_evidence.py`, `tests/`, `examples/`, `LICENSE` 이고 `README.md`, `assets/`, `.gitignore` 는 스킬 동작과 무관해 뺐다. 위키 데이터(`raw/`, `wiki/`)는 일상정보가 들어가므로 이 저장소에 두지 않고 별도 저장소에 둔다.
- `cog-llm-wiki` 시험(2026-11-13): `tests/` 52개 통과. 한국어 위키 문서에서 `check_evidence.py` 가 원문에 없는 수치·날짜·인용을 잡고 있는 값은 잡지 않았다(작은 사례 1벌).
