# 파일 위치와 구조

Vue + Vite SPA 의 배치 규칙. 앱 폴더 구성(apps/분류/화면)은 프로젝트 하나(infra-iscim-app)에서 뽑은 것이며, 메뉴 구조가 있는 관리형 SPA 를 전제함.

## 버킷은 둘뿐
| 조건 | 위치 |
|---|---|
| 한 앱만 씀(소유자가 있음) | `src/apps/<분류>/<화면>/` (분류 없는 1단 화면은 `src/apps/<화면>/`) |
| 두 앱 이상이 씀(소유자가 없음) | `src/` 의 해당 레이어 |

- 경계는 얼마나 전역적인가가 아니라 소유자가 있는가로 읽음. 막는 실수: 전역은 아닌데 공유해야 하는 애매한 칸이 생기는 일.
- shared/ 폴더를 만들지 않음. shared 는 무엇인가가 아니라 몇 군데서 쓰이는가를 이름으로 삼아, 사용처가 바뀌면 이름이 거짓이 되고 쓰레기통이 됨.
- 전역 레이어 안에서는 성격별로 나눔(components/page, components/data-table). 이름이 누가 쓰는지가 아니라 무엇인지를 말해야 함.

## 앱은 서로 임포트하지 않음
- apps/A 에서 apps/B 를 임포트하지 않음. 임포트하고 싶어지는 순간이 전역으로 올리라는 신호임.
- 승격은 미리 하지 않고 두 번째 앱이 실제로 필요해질 때 옮김. 옮기는 비용은 디렉토리와 임포트 경로뿐임.
- 예외는 금지하지 않고 표로 세어 관리함. 새 예외를 만들기 전에 사용자에게 묻고, 표가 길어지면 앱 경계를 다시 봄. 예시 프로젝트의 예외는 router/routes.ts 의 글롭 하나와 홈 화면이 앱의 상태 카드를 놓는 것 둘임.
- 이 금지는 린트 규칙(import/no-restricted-paths 류)을 걸지 않으면 아무것도 막지 않음. 검사되고 있는지 먼저 확인함.

## 앱 하나의 표준 구성
앱 폴더는 메뉴 모양을 따르고 이름은 다루는 데이터로 지음. 1단 화면에 한 단을 더 만들지 않음(apps/org/department 로 두면 메뉴에 없는 2단을 말함). API 주소도 같은 모양임.

```
src/apps/<분류>/<화면>/
├── api/          URL 빌더만. HTTP 는 스토어가 함
├── components/   이 앱 전용 컴포넌트
├── definitions/  여러 곳이 쓰는 고정 값(사전, 폼 스키마, 필터)
├── pages/        라우트가 가리키는 화면
├── router/       routes.ts
├── stores/       이 앱 전용 스토어. 서버 호출은 전부 여기
├── types/        이 앱 전용 타입
└── utils/        이 앱만 쓰는 순수 함수
```

필요한 폴더만 만듦. 이름은 성격이, 자리는 소유가 정함.

| 성격 | 한 앱만 씀 | 두 앱 이상이 씀 |
|---|---|---|
| 고정 값 | `apps/<앱>/definitions/` | `src/definitions/` |
| 순수 함수 | `apps/<앱>/utils/` | `src/utils/` |

- 컴포넌트는 앱을 아느냐로 가름. 앱의 타입과 스토어와 라벨을 모르는 부품은 쓰는 앱이 하나여도 `src/components/` 에 둠.
- 함수와 컴포저블의 자리는 셋 중 하나임. 두 앱 이상이 쓰면 전역, 한 앱 안에서만 여러 곳이 쓰면 그 앱의 utils, 한 앱만 써도 앱을 모르는 성격이면 전역.
- router/routes.ts 는 어디에도 등록하지 않음. 전역 라우터가 `@/apps/**/router/routes.ts` 를 글롭으로 모으므로 파일을 놓기만 하면 됨. 막는 실수: 중앙 라우트 파일의 충돌과 등록 누락.

### definitions/
- 고정 값은 폴더로 나누지 않고 파일 이름으로 가름: `<가족>Constants.ts`(코드가 값을 찾아 쓰는 사전), `<가족>FormSchema.ts`(폼에 통째로 넘기는 스키마), `<가족>Filters.ts`(목록 필터 선언).
- definitions/ 에는 함수를 두지 않음. 값 안에 든 한 줄 함수(컬럼의 cell)는 값의 일부이고, 판별과 포매터 함수는 utils/ 임.
- 3줄로 끝나는 선언은 그 화면에 둠. 한 컴포넌트만 쓰는 선언(표의 컬럼)은 그 컴포넌트 옆에 둠. 여러 곳이 쓰는 값만 definitions/ 에 남김.
- 폼 스키마(valibot 등)는 런타임 값이므로 types/ 가 아니라 definitions/ 에 둠. 스키마에서 뽑은 타입은 types/ 임. 막는 실수: 같은 경로가 값 임포트와 타입 임포트로 두 번 나오는 일.
- 폴더 나눔은 파일 이름이 소유를 말하지 못할 때만 함(memberConstants.ts 는 평평하게, ReportModal.vue 는 폴더로). definitions, stores, types 는 평평함.

### components/
- 앱 안에서 파일을 나누는 것은 승격이 아님. 한 화면만 쓰는 조각도 나눠 두면 다른 자리에 고치지 않고 옮겨 쓸 수 있음.
- 앱에 화면(탭)이 여럿이면 쓰는 화면으로 먼저 가르고, 화면 폴더 안은 종류로 다시 가름. 화면 폴더 밖의 조각은 앱 전체가 씀.
- 종류 폴더 이름은 modal, table, list, panel, tree, report, card 를 씀. 모달도 표도 아닌 조각이 나오면 그때 종류 이름을 정함.
- common/ 폴더를 만들지 않음. 폴더에 안 든 것이 공통이라는 약속으로 충분하고, common 은 아무거나 들어가는 서랍이 됨.
- 폴더 이름은 스토어와 컬럼과 같은 가족 이름을 씀(DeployUserPage, stores/deployUser.ts, components/deployUser/list/DeployUserList.vue).
- 폴더 밖에 파일을 두지 않음. 여러 앱이 쓰는 것만 전역 `src/components/` 에 둠.

## 전역 레이어
| 디렉토리 | 담는 것 |
|---|---|
| `api/` | 특정 앱 것이 아닌 API URL |
| `components/` | 소유자 없는 컴포넌트. 성격별 하위 디렉토리(data-table, detail, page, modal, input, state). 모달 안에서도 쓰는 것을 page/ 에 두지 않음 |
| `composables/` | 공용 훅 |
| `definitions/` | 여러 앱이 쓰는 고정 값 |
| `layouts/` | 앱 셸 |
| `pages/` | 메뉴에 속하지 않는 화면 |
| `plugins/` | 부팅 시 주입과 서버 호출 인스턴스(axios, pinia) |
| `router/` | 라우터 조립과 가드 |
| `stores/` | 전역 상태 |
| `style/` | 전역 CSS 와 테마 |
| `types/` | 여러 레이어가 공유하는 타입, 주인이 없는 백엔드 응답 모양 |
| `utils/` | 순수 함수. formatters(값 하나를 보일 글자로), converters(값을 다른 모양으로, to결과), validators(값이 맞는 모양인가, is모양). 파일은 하는 일로 나누고 formUtils 처럼 주제로 나누지 않음 |

- 전역은 레이어로만 나누고 가족(data-table)은 폴더와 이름으로 묶음(components/data-table, useList*, types/data-table.ts). kits/ 같은 두 번째 축을 두지 않음. 막는 실수: 키트냐 레이어냐를 매번 먼저 판단하게 되는 일.
- 컴포저블(use*)은 반응형과 생명주기와 주입을 가지며 setup 안에서만 부름. ref, inject, 생명주기가 없으면 use 를 붙이지 않음. 막는 실수: setup 밖의 평범한 모듈에서 못 쓰게 되는 일.
- 전역 utils/ 는 어느 도메인의 상수도 가져오지 않음. 앱 utils/ 는 자기 도메인을 알아도 됨. 두 앱 이상이 쓰는 사전은 전역이고, 한 앱만 쓰는 동안은 그 앱의 definitions/ 임.
- 사전은 `satisfies Record<string, string>` 으로 둠. `: Record<string, string>` 으로 붙이면 키 목록을 잊어 오타 키가 통과함. 서버 키로 찾는 자리만 넓혀 읽음.
- 한 줄로 끝나는 것을 감싸는 함수와 함수를 돌려주는 함수를 만들지 않음. 값을 받아 값을 돌려주게 씀.

## 타입 위치는 의존 방향을 따름
아무것도 임포트하지 않는 것이 아래층이고, 아래층 것을 위층으로 올리면 순환이 됨.

| 타입 | 위치 |
|---|---|
| 주인이 앱인 엔드포인트의 요청과 응답 모양 | `apps/<앱>/types/` |
| 주인이 없는 엔드포인트(프로필, 인증, 페이지네이션, 에러, 선택지) | 전역 `types/` (쓰는 곳 수와 무관) |
| 컴포넌트나 컴포저블의 옵션 타입 | 그 파일에서 export (쓰는 곳 수와 무관) |
| 여러 파일이 쓰는 화면 상태 | 전역 `types/` 또는 앱 `types/` |
| 한 파일만 쓰는 타입 | 그 파일 안, export 하지 않음. 본문을 가리면 `<파일>.types.ts` |

- 백엔드 모양은 한곳에 모음. 막는 실수: 서버가 칸 이름을 바꿀 때 어디에 적혀 있는지 찾아 헤매는 일.
- 타입 파일 안에서는 interface 를 먼저, type 을 나중에 둠.
- .d.ts 안의 깨진 임포트는 skipLibCheck 때문에 vue-tsc 가 잡지 못함. 타입 augmentation(types/vue-router.d.ts)을 고쳤으면 일부러 틀린 값을 넣어 오류가 나는지 확인함. 막는 실수: 라우트 메타가 any 로 퇴화해도 오류가 없는 일.

## 단수와 복수
안에 든 것이 그 이름의 복수인지로 정함. components, stores, pages, types 는 복수이고, router(라우터 하나를 쪼갠 부품), style(css 와 theme 두 종류), api(셀 수 없는 명사)는 단수임.
