# cog-vue-uikit

공용 UI 부품으로 화면을 만들 때 지키는 화면 패턴 규칙. 각 규칙에는 막으려는 실수를 함께 적음. 파일 위치, 이름, 스토어, 스타일 토큰 같은 기본 규칙은 `cog-vue` 가 정하고 이 스킬은 그 위에서 화면 패턴만 다룸.

예시의 App* 부품과 use* 컴포저블은 예시를 가져온 프로젝트의 것임. 다른 저장소에서는 같은 일을 하는 부품에 같은 규칙을 적용하고, 부품이 아직 없으면 만들기 전에 사용자에게 물음.

## 먼저 할 일
1. 프로젝트의 UI 라이브러리를 package.json 으로 확인함(예: @nuxt/ui).
2. `references/frameworks/` 에 그 라이브러리의 폴더가 있으면 해당 패턴 파일을 `references/common.md` 와 함께 읽음.
3. 폴더가 없으면 common.md 의 원칙만 적용하고, 라이브러리별 구현 규칙이 없다고 사용자에게 알림. 그 라이브러리의 공식 문서를 확인해 구현하고, 새 폴더로 남길지 사용자에게 물음.

## 항상 지킬 것
1. 목록 화면의 조건(검색, 필터, 정렬, 페이지), 결과(행, 건수, 로딩, 실패), 선택(고른 행)은 컴포저블 셋으로 나누고 페이지가 이음. 막는 실수: 화면마다 watcher 를 엮어 요청이 두 번 나가거나 늦은 응답이 화면을 덮는 일.
2. 선택지(셀렉트 항목)는 화면에 적지 않고 서버에서 받음. 막는 실수: 서버가 라벨을 고쳐도 모달만 옛 라벨로 남는 일.
3. 토스트는 공용 래퍼 하나로만 띄우고 UI 라이브러리의 토스트 함수를 직접 부르지 않음. 막는 실수: 색과 아이콘과 제목 규칙이 화면마다 갈리는 일.
4. 실패 사유는 서버가 준 문장을 그대로 보여 주고 화면이 지어내지 않음. 막는 실수: 서버가 이유를 줬는데 코드 문자열만 보이는 일.
5. 권한 없는 버튼은 숨기기만 하고 막는 것은 서버가 함. 막는 실수: 화면의 권한 분기가 서버와 어긋나는 일.
6. 확인 모달의 로딩과 닫기는 모달이 갖고, 실패하면 모달을 닫지 않고 모달 안에서 사유를 말함. 막는 실수: 호출부마다 순서가 달라 모달이 안 닫히거나 로딩이 안 꺼지는 일.
7. 폼 검증은 폼 컴포넌트와 스키마로 하고 에러 상태를 손으로 들지 않음. 서버가 준 필드 에러는 폼에 넣음. 막는 실수: 검증은 도는데 화면에 말이 안 나오는 일.
8. 열자마자 한 건을 가져오는 모달은 prop 으로 id 하나만 받고 스스로 가져옴. 막는 실수: 목록 응답과 상세 응답 두 곳의 값이 섞여 일부 칸만 낡는 일.
9. 만들고 지운 뒤에도 사용자가 보던 페이지와 걸어 둔 필터를 유지함. 막는 실수: 3페이지를 보던 사용자가 1페이지로 쫓겨나는 일.

## 무엇을 읽을지
| 상황 | 읽을 파일 |
|---|---|
| 모든 화면 패턴의 프레임워크 무관 원칙 | `references/common.md` |
| @nuxt/ui 프로젝트: 목록 화면(표 컬럼 너비, 정렬 헤더, 행 클릭, 뱃지, 필터 배치) | `references/frameworks/nuxt-ui/data-list.md` |
| @nuxt/ui 프로젝트: 읽기 전용 상세(열 수, 분할 화면, 타일) | `references/frameworks/nuxt-ui/detail-view.md` |
| @nuxt/ui 프로젝트: 페이지 헤더, 액션과 건수 배치, 아이콘 크기 | `references/frameworks/nuxt-ui/page-header.md` |
| @nuxt/ui 프로젝트: 토스트, 모달, 폼 검증, 에러 표시 | `references/frameworks/nuxt-ui/feedback-form.md` |

## 이 스킬에 두지 않는 것
- 파일 위치, 앱 경계, 이름 짓기, 스토어 작성, 색과 타이포와 아이콘 토큰은 `cog-vue`
- @nuxt/ui 컴포넌트 자체의 API 와 선택 기준(설치되어 있으면 nuxt-ui 스킬을 따로 읽음)
- 서버가 줄 필드와 선택지와 API 모양을 바꾸는 일은 `cog-django`
- 저장소가 지금 어떻게 생겼는지(부품 목록, 화면 목록)는 규칙이 아니라 그 저장소의 문서에 둠
